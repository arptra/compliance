# Как пользоваться DeepSeek + OpenSpec без технических знаний

Комплект предназначен для больших репозиториев, которые невозможно целиком
поместить в контекст локальной модели. DeepSeek обрабатывает проект частями,
сохраняет прогресс на диске и сам собирает нужный контекст для каждой задачи.

Пользователю не нужно разбираться в модулях, Gradle, bounded contexts,
субагентах или лимитах токенов.

## Что вставить в CLI

Откройте DeepSeek CLI в корне нужного репозитория и напишите:

```text
Прочитай `/path/to/prompts/deepseek-openspec/START_HERE.md`, строго следуй ему для текущего репозитория, отвечай по-русски и оставь простой интерактивный режим.
```

Замените путь на настоящий путь к комплекту промптов.

## Первый запуск

DeepSeek покажет простое меню:

```text
# Документация репозитория

OpenSpec ещё не настроен.

1. Полностью проанализировать репозиторий и создать текущее SDD.
2. Создать только быструю основу OpenSpec.
3. Показать план анализа, ничего не изменяя.
4. Остановиться.

Ответьте цифрой 1-4.
```

Для большого старого проекта выбирайте `1`. DeepSeek один раз спросит
подтверждение. После ответа `YES` он самостоятельно:

1. составит реестр всего репозитория;
2. исключит generated/vendor/binary/output и секретные области с объяснением;
3. разобьёт полезный код на модули и домены;
4. запустит доступных субагентов параллельно;
5. извлечёт точные команды, параметры, aliases, defaults и настройки окружения;
6. извлечёт API, события, данные, тестовое и runtime-поведение;
7. создаст capability-specs и граф связей;
8. проверит пропуски независимым auditor-агентом;
9. сохранит итоговый статус и понятный отчёт.

Production-код во время инициализации не меняется.

## Что будет видно во время долгой инициализации

Вместо технических логов DeepSeek показывает короткий статус:

```text
Фаза: анализ поведения
Задачи: 148/230
Пути репозитория классифицированы: 100%
Capabilities описано: 74
Явных пробелов: 6
Статус: выполняется
```

Можно закрыть CLI и вернуться позже. Состояние и очередь сохраняются в
`openspec/bootstrap/`. При следующем запуске выберите продолжение с checkpoint;
завершённые области повторно анализироваться не должны.

## Что означают итоговые статусы

- `READY`: все проверки полноты прошли.
- `READY_WITH_DECLARED_GAPS`: весь доступный проект обработан, но найдены явно
  записанные неизвестные факты, противоречия или отсутствующие тесты/контракты.
- `IN_PROGRESS`: обработка ещё не закончена.
- `BLOCKED`: для продолжения действительно не хватает доступа или внешней
  информации.

Статус с пробелами честнее выдуманного «полного» описания: DeepSeek показывает,
что именно невозможно доказать по репозиторию.

## Обычная работа после инициализации

DeepSeek показывает меню:

```text
# OpenSpec

1. Задать точный вопрос о текущем репозитории.
2. Работать с тикетами, найденными в истории Git.
3. Описать новую фичу или изменение.
4. Описать изменение и реализовать его после подтверждения.
5. Продолжить незавершённую работу.
6. Исправить ошибку теста, сборки или запуска.
7. Обновить документацию после изменений репозитория.
8. Показать покрытие, неизвестные факты или противоречия.
9. Архивировать завершённое изменение.
10. Остановиться.
```

Можно не выбирать цифру, а сразу написать одну фразу:

```text
Добавь экспорт отчёта в Excel с фильтрами по дате и статусу.
```

DeepSeek сам найдёт затронутые capabilities, контракты, код и тесты. Он создаст
небольшой context packet только для этой задачи, подготовит OpenSpec change и
один раз спросит разрешение на реализацию.

## Как задавать вопросы о репозитории

Можно сразу спросить без выбора пункта меню:

```text
Какой точный параметр включает повторную обработку ошибок и какое у него значение по умолчанию?
```

DeepSeek обязан сначала проверить `openspec/index/commands.yml`, затем открыть
связанный код или тест. Если индекс отсутствует или устарел, он ищет реальное
объявление команды и при необходимости безопасно проверяет `--help`.

Допустимые результаты:

- `VERIFIED_FROM_SPEC`: свежая спека подтверждена связанным evidence;
- `VERIFIED_FROM_CODE`: точное объявление найдено в текущем коде;
- `VERIFIED_FROM_RUNTIME`: параметр подтверждён безопасным текущим help;
- `VERIFIED_FROM_TEST`: поведение подтверждено тестом;
- `CONFLICTING_EVIDENCE`: источники противоречат друг другу;
- `NOT_VERIFIED`: точного доказательства нет.

При `NOT_VERIFIED` DeepSeek показывает, где искал, и ближайшие подходящие места,
но не выдаёт похожий параметр за настоящий. Exact flag, default, alias, env var,
config key, API field или build task должны буквально присутствовать в
проверенном источнике.

## Как собрать тикеты из истории Git

Выберите пункт `2` или сразу напишите:

```text
Проиндексируй все тикеты из истории Git.
```

DeepSeek задаст один вопрос:

```text
Как выглядит префикс тикета до номера, включая разделитель?
Например: PROJ- для тикетов PROJ-123.
```

Нужно написать точный префикс, например `PROJ-`. DeepSeek не станет сам
додумывать варианты `PROJ123`, `PROJ_123` или `PROJ 123`.

После этого локальный parser просмотрит commits из всех refs, reflog, Git notes
и названия веток/тегов. `git fetch` и обращения к Jira/GitHub не выполняются.
Найденные записи сохраняются здесь:

```text
openspec/history/git-tickets/
```

Полные patches и bodies сообщений постоянно не сохраняются. Субагенты получают
небольшие группы тикетов, параллельно изучают commits, diff, текущий код, тесты
и контракты, затем записывают отдельную карточку каждого тикета.

Чтобы посмотреть результат, напишите:

```text
Покажи тикет PROJ-123 с кодом и описанием.
```

DeepSeek покажет:

- что изменили по данным Git;
- связанные commits;
- ключевой код и diff на момент тикета;
- где реализация находится сейчас;
- тесты, контракты, миграции и настройки;
- более поздние изменения этого кода;
- неоднозначности, например commit сразу с несколькими тикетами.

После перезапуска CLI готовые карточки не анализируются заново. Повторное
сканирование сохраняет `completed` для неизменившихся тикетов и ставит в очередь
только новые или `stale` записи.

## Как используется мощность локальной модели

Если CLI умеет создавать настоящих субагентов, DeepSeek параллельно запускает
независимые задачи: архитектура, домены, команды, контракты, данные, тесты,
runtime и аудит полноты. Для ответа на точный вопрос отдельный validator-агент
повторно открывает источники и проверяет каждое утверждение. Если такого API
нет, DeepSeek выполняет отдельный второй проверочный проход сам.

DeepSeek не должен писать, что использовал субагентов, если среда на самом деле
их не предоставляет.

### Что происходит при HTTP 429

Каждый реальный ответ HTTP `429` сразу появляется в техническом логе. DeepSeek
также показывает короткое сообщение пользователю: параллельный запуск
остановлен, ожидающие запросы поставлены в одну общую FIFO-очередь,
`concurrency=1`.

Уже отправленные запросы могут завершиться, но новые параллельные slots не
открываются. Workers не запускают собственные retry-loop. Coordinator учитывает
`Retry-After` либо использует ограниченный backoff, сохраняет очередь на диск и
после перезапуска CLI продолжает её последовательно. Timeout, OOM и обычная
сетевая ошибка не выдаются за 429.

## Почему полный SDD не загружается в модель

Полное описание хранится в `openspec/specs/` и индексах `openspec/index/`.
Перед каждой задачей DeepSeek выбирает из графа только:

- затронутые требования;
- зависимости и обратные зависимости;
- нужные контракты и данные;
- соответствующий код и тесты;
- применимые правила безопасности и надёжности.

Если обязательный контекст не помещается, задача делится на несколько частей.
Критические контракты и инварианты не должны теряться из-за агрессивного
сжатия.

## Как обновлять промпты поверх существующей версии

Можно заменить содержимое папки `prompts/deepseek-openspec/` новой версией и
снова запустить тот же `START_HERE.md`. Текущий pack хранит свою версию в
`prompt-pack.yml`, а целевой репозиторий запоминает применённую версию и hash в
`openspec/meta.yml`.

При различии DeepSeek покажет простое меню обновления:

```text
1. Безопасно обновить OpenSpec и новые индексы.
2. Только показать план миграции.
3. Продолжить в режиме совместимости без изменений.
4. Остановиться.
```

Миграция не переписывает готовые specs, active changes, очередь, findings и
пользовательские поля. Она добавляет недостающие структуры и запускает только
целевой backfill. Например, новый command index строится по CLI/build/config
файлам без повторного анализа всех доменов.

Каждая миграция имеет ID, checkpoint и проверку повторного запуска. Уже
применённая миграция при втором запуске не должна создавать новых изменений.

## Когда DeepSeek снова задаст вопрос

Он должен спрашивать только когда:

- нужно первое подтверждение полной инициализации;
- нужно один раз подтвердить неразрушающую миграцию новой версии prompt pack;
- бизнес-решение нельзя безопасно восстановить по коду и спецификациям;
- пора разрешить изменение production-кода;
- изменение неожиданно расширило пользовательский или рискованный scope;
- требуется commit, push, удаление, установка или destructive-команда.

Для внутренних batch-задач, выбора файлов и запуска read-only субагентов
дополнительные подтверждения не нужны.
